## 1. How `SaveChanges` Actually Works

### 1.1 The Implicit Transaction

Session 6, Section 7.2 introduced `DbContext` as a Unit of Work: every tracked `Added`, `Modified`, and `Deleted` entity commits together in a single call to `SaveChanges`. What that section didn't spell out is *how* — every call to `SaveChanges`/`SaveChangesAsync` runs inside its own database transaction automatically, even when it's producing several `INSERT`/`UPDATE`/`DELETE` statements at once.

```csharp
team.Name = "Al Ahly SC";
_dbContext.Players.Add(newSigning);
_dbContext.Players.Remove(retiredPlayer);

await _dbContext.SaveChangesAsync();
// All three statements run inside ONE transaction. If any one fails, EF Core
// rolls the whole batch back — the database never ends up with only some of
// these three changes applied.
```

**Why this matters:** without this guarantee, a failure partway through (a constraint violation on the second statement, a dropped connection) could leave the database in a state that reflects only part of an intended change — the new signing added, but the team name update lost. The implicit per-`SaveChanges` transaction is what keeps "everything in this call succeeds, or none of it does" true by default, with no code written for it.

### 1.2 Explicit Transactions Across Multiple `SaveChanges` Calls

Sometimes a single logical operation genuinely needs more than one `SaveChanges` call — for instance, if an ID generated by the first `SaveChanges` is needed before the second set of changes can be built. The implicit per-call transaction from Section 1.1 doesn't cover that; each `SaveChanges` call gets its own separate transaction by default, which means the two calls could succeed and fail independently.

```csharp
using var transaction = await _dbContext.Database.BeginTransactionAsync();
try
{
    var team = new Team { Name = "Pyramids FC" };
    _dbContext.Teams.Add(team);
    await _dbContext.SaveChangesAsync();   // team.Id is now populated

    _dbContext.Players.Add(new Player { Name = "New Signing", TeamId = team.Id });
    await _dbContext.SaveChangesAsync();

    await transaction.CommitAsync();
}
catch
{
    await transaction.RollbackAsync();
    throw;
}
```

**Why this is worth knowing rather than just always wrapping everything in one:** an explicit transaction has real cost — it holds database locks open for longer, across more round trips, which increases contention under concurrent load. Reach for it specifically when two or more separate `SaveChanges` calls need to be treated as one atomic unit; for the ordinary case of a single `SaveChanges` call handling everything, Section 1.1's implicit transaction is already correct and requires no extra code.

## 2. Optimistic Concurrency

### 2.1 The Problem

Two users load the same `Player`, both edit different fields, and both save. Without any concurrency handling, the second save silently overwrites the first — not with a conflict, just a quiet, invisible loss of the first user's change.

### 2.2 A Concurrency Token

```csharp
public class Player
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public int Goals { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } = Array.Empty<byte>();
}
```

`[Timestamp]` (or, via Fluent API, `.IsRowVersion()`) marks a column that the database automatically updates every time the row changes. EF Core includes that column's value in the `WHERE` clause of every `UPDATE`/`DELETE` it generates for that entity:

```sql
UPDATE Players SET Goals = @goals
WHERE Id = @id AND RowVersion = @originalRowVersion
```

If another process already changed the row since it was loaded, `RowVersion` no longer matches, zero rows match the `WHERE` clause, and EF Core detects that zero rows were affected and throws `DbUpdateConcurrencyException` — instead of silently succeeding and overwriting the other change.

```csharp
try
{
    await _dbContext.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    var entry = ex.Entries.Single();
    var databaseValues = await entry.GetDatabaseValuesAsync();
    // Decide here: reload and let the user retry, merge the two sets of changes,
    // or overwrite deliberately — whichever fits the situation, but now as an
    // explicit decision instead of a silent, accidental one.
}
```

**This is called "optimistic" concurrency because of what it *doesn't* do:** it never locks the row while someone has it loaded — any number of users can load the same `Player` and start editing simultaneously. It only checks for a genuine conflict at the moment of saving, optimistically assuming conflicts will be rare. Row-level locking (holding a lock for the whole time a row is "being edited") is the pessimistic alternative, and it's rarely worth the throughput cost it imposes for typical web application workloads.

### 2.3 A Related Constraint Failure — `DbUpdateException`

`DbUpdateConcurrencyException` is specifically about a row-version mismatch. A separate, more common exception covers everything else the database itself rejects — a unique index violation, a required column left null at the database level, a foreign key pointing at a row that doesn't exist:

```csharp
try
{
    _dbContext.Players.Add(new Player { Name = "Salah", JerseyNumber = 11 });   // 11 already taken on this team
    await _dbContext.SaveChangesAsync();
}
catch (DbUpdateException ex)
{
    // ex.InnerException typically holds the actual database driver's error
    // (e.g. a SqlException with a unique-constraint violation number).
    // Inspect it to distinguish "duplicate jersey number" from "connection dropped"
    // rather than treating every DbUpdateException the same way.
}
```

**Why this is worth handling deliberately rather than letting it bubble up as a generic 500:** a unique constraint violation (two players with the same jersey number on the same team) is a predictable, meaningful business situation, not a bug — the difference between a caught `DbUpdateException` translated into "that jersey number is already taken" and an unhandled exception crashing the request is entirely in whether this is anticipated in the code that calls `SaveChangesAsync`.

## 3. Raw SQL, Deliberately

### 3.1 When LINQ Genuinely Isn't Enough

Session 5, Section 7.4 already covered why some C# expressions can't be translated to SQL at all. EF Core also provides an escape hatch for queries that are valid SQL but awkward or impossible to express through LINQ cleanly — a recursive common table expression, a database-specific function, a query already tuned by a DBA.

```csharp
var topScorers = await _dbContext.Players
    .FromSqlInterpolated($"SELECT * FROM Players WHERE Goals > {minGoals} ORDER BY Goals DESC")
    .ToListAsync();
```

**Why `FromSqlInterpolated` specifically, and not string concatenation:** the interpolated `{minGoals}` is automatically converted into a parameterized query argument, not pasted directly into the SQL text. This is exactly the same reasoning as parameterized ADO.NET commands — it's what prevents SQL injection. `FromSqlRaw` exists for cases needing more manual control, but it requires manually adding parameters correctly; reaching for `FromSqlInterpolated` by default removes an entire category of mistake.

```csharp
// Non-query SQL — schema maintenance, bulk operations LINQ can't express as an update
await _dbContext.Database.ExecuteSqlInterpolatedAsync(
    $"UPDATE Players SET IsInjured = 0 WHERE TeamId = {teamId}");
```

### 3.2 When Reaching for Raw SQL Is a Smell, Not a Solution

If raw SQL starts showing up because a LINQ query *would* translate but performs poorly, that's usually a signal to look at indexing (Section 6) or restructure the LINQ query first, rather than reaching for raw SQL as the default fix. Raw SQL loses compile-time checking against the model, doesn't get the same automatic parameterization safety as `FromSqlInterpolated` if written carelessly with `FromSqlRaw`, and reintroduces exactly the untyped-string risk an ORM exists to remove (Session 6, Section 1.1). It's a deliberate, occasional tool — not a fallback for "LINQ syntax felt awkward this one time."

Section 4 also covers a specific case (bulk updates and deletes) that used to be a common reason to reach for raw SQL, and now has a purpose-built LINQ-based alternative instead.

## 4. Bulk Operations — `ExecuteUpdate` and `ExecuteDelete`

### 4.1 The Problem: "Load, Mutate, Save" Doesn't Scale

Session 6, Section 6.3's ordinary update pattern — load the entity, mutate it, call `SaveChangesAsync` — is correct and idiomatic for updating one row, or a handful. It stops being reasonable for a bulk change:

```csharp
// Marking every player on a relegated team as inactive — one row at a time
var players = await _dbContext.Players.Where(p => p.TeamId == teamId).ToListAsync();
foreach (var player in players)
{
    player.IsActive = false;
}
await _dbContext.SaveChangesAsync();
```

This pulls every matching row across the network into memory, snapshots each one in the change tracker (Session 6, Section 7), and then sends back one `UPDATE` statement per row — for what is conceptually a single, simple operation. For a handful of rows this is invisible; for thousands, it's a genuine performance problem, and it's exactly the kind of case that used to push people toward raw SQL (Section 3) just to get one `UPDATE ... WHERE` statement instead.

### 4.2 `ExecuteUpdate` and `ExecuteDelete`

```csharp
// One UPDATE statement, generated from LINQ, with no entities loaded into memory at all
await _dbContext.Players
    .Where(p => p.TeamId == teamId)
    .ExecuteUpdateAsync(setters => setters.SetProperty(p => p.IsActive, false));

// Multiple columns in one call
await _dbContext.Players
    .Where(p => p.TeamId == teamId && p.IsInjured)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(p => p.IsActive, false)
        .SetProperty(p => p.Status, PlayerStatus.Injured));

// The delete equivalent — one DELETE statement, no entities loaded first
await _dbContext.Players
    .Where(p => p.RetiredDate < DateTime.UtcNow.AddYears(-5))
    .ExecuteDeleteAsync();
```

Both methods translate a LINQ query directly into a single `UPDATE`/`DELETE` statement executed straight against the database — no `SELECT` to load rows, no change tracker involvement, no per-row round trip.

**Why this matters:** it's the same category of win as `Include` fixing N+1 (Session 7 Section 5.2) — collapsing what would otherwise be many round trips (or an awkward load-everything-into-memory step) into exactly one statement that does the whole job on the database server itself.

### 4.3 What These Bypass — and Why That's a Real Tradeoff, Not Just a Detail

`ExecuteUpdate`/`ExecuteDelete` skip the change tracker entirely, which has consequences worth knowing before reaching for them:

- **No optimistic concurrency check (Section 2.2).** A row-version/`[Timestamp]` column is not consulted — the statement updates whatever currently matches the `Where` clause, regardless of whether it's changed since anyone last read it. Bulk operations are for cases where that per-row conflict detection genuinely doesn't apply (a scheduled cleanup job, a bulk status reset), not as a shortcut around it for user-driven edits.
- **No `SaveChangesAsync` call, and no implicit transaction shared with other pending changes.** Each `ExecuteUpdateAsync`/`ExecuteDeleteAsync` call runs immediately, on its own — it does not wait for a later `SaveChangesAsync`, and it is not automatically batched together with other tracked changes still pending in the same `DbContext`. If a bulk operation needs to be atomic together with other changes, wrap them together in an explicit transaction (Section 1.2).
- **Any already-tracked entities matching the same rows are not updated in memory.** If a `Player` was already loaded and is being held onto after an `ExecuteUpdateAsync` bulk-changes that same row, the in-memory object is now silently stale until it's reloaded.

**Q: So when is "load, mutate, `SaveChanges`" still the right choice over a bulk operation?**

>When there's genuinely one entity (or a small, bounded few) being changed, when per-row concurrency checking matters, or when other business logic needs to run per entity as part of the update (validation, raising a domain event, cascading side effects). `ExecuteUpdate`/`ExecuteDelete` are for the specific case of a set-based change applied uniformly to many rows, with no per-row logic needed beyond the `Where` clause itself.

## 5. Design Patterns on Top of EF Core

### 5.1 `DbContext` Is Already a Unit of Work

Session 6, Section 7.2 named this explicitly: a single `DbContext`, accumulating changes and committing them together via `SaveChanges`, already *is* the Unit of Work pattern. This section is about the pattern most commonly built *on top of* it: the Repository.

### 5.2 The Repository Pattern

```csharp
public interface IPlayerRepository
{
    Task<Player?> GetByIdAsync(int id, CancellationToken cancellationToken);
    Task<List<Player>> GetTopScorersAsync(int count, CancellationToken cancellationToken);
    Task AddAsync(Player player, CancellationToken cancellationToken);
}

public class PlayerRepository : IPlayerRepository
{
    private readonly LeagueDbContext _dbContext;
    public PlayerRepository(LeagueDbContext dbContext) => _dbContext = dbContext;

    public Task<Player?> GetByIdAsync(int id, CancellationToken cancellationToken) =>
        _dbContext.Players.FirstOrDefaultAsync(p => p.Id == id, cancellationToken);

    public Task<List<Player>> GetTopScorersAsync(int count, CancellationToken cancellationToken) =>
        _dbContext.Players.OrderByDescending(p => p.Goals).Take(count).ToListAsync(cancellationToken);

    public async Task AddAsync(Player player, CancellationToken cancellationToken)
    {
        await _dbContext.Players.AddAsync(player, cancellationToken);
        await _dbContext.SaveChangesAsync(cancellationToken);
    }
}
```

**What this buys you:** code that depends on `IPlayerRepository` instead of `LeagueDbContext` directly doesn't know or care that EF Core is the persistence mechanism at all — it could be swapped for an in-memory fake in a unit test with no EF Core involved, or for an entirely different storage technology later, without changing a single caller. It's also a concrete, named place to enforce the "return `List<T>`, never `IQueryable<T>`" boundary from Session 5, Section 10.4 — `IPlayerRepository`'s methods return materialized data, never a leaked, still-composable `IQueryable<T>`.

**What this costs you, honestly:** `DbContext` and `DbSet<T>` already give you most of this — a queryable, testable (via the EF Core in-memory or SQLite providers, Section 7.3), well-designed abstraction. Wrapping it in a repository interface with one method per query need can turn into a lot of near-identical boilerplate methods, each a thin pass-through, for a project that was never actually going to swap out EF Core. This is a genuine, debated tradeoff in the .NET community, not a settled "always do this."

**When it's clearly worth it:** the codebase has real reasons to isolate persistence (heavy unit testing without a database, a plausible future migration off EF Core, multiple bounded contexts that shouldn't share direct `DbContext` access). When those reasons aren't present, working directly against `DbContext`/`DbSet<T>` — which is already reasonably testable and already an abstraction over raw ADO.NET — is a legitimate, simpler choice, and plenty of well-built EF Core codebases do exactly that.

### 5.3 The Factory Pattern — `IDbContextFactory<T>`

Session 6, Section 4.1 flagged this scenario: code that isn't scoped to a single request (a background service, a Blazor component managing its own lifetime) can't just inject a `Scoped` `DbContext` the normal way.

```csharp
builder.Services.AddDbContextFactory<LeagueDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("League")));

public class NightlyReportJob
{
    private readonly IDbContextFactory<LeagueDbContext> _contextFactory;
    public NightlyReportJob(IDbContextFactory<LeagueDbContext> contextFactory) => _contextFactory = contextFactory;

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        await using var dbContext = await _contextFactory.CreateDbContextAsync(cancellationToken);
        var reports = await dbContext.Teams.Select(t => new { t.Name, Count = t.Players.Count }).ToListAsync(cancellationToken);
        // ... use reports, then dbContext is disposed at the end of this method
    }
}
```

This is the **Factory pattern**, doing exactly what it always does: providing a way to create correctly-configured instances of something on demand, so the caller doesn't need to know how to construct one itself. `CreateDbContextAsync()` hands back a fresh, independent `DbContext`, each call, decoupled from any HTTP request scope — appropriate for exactly the long-lived-service and manual-lifetime cases the DI container's normal `Scoped` registration doesn't fit.

### 5.4 The Options Pattern

`AddDbContext`'s configuration delegate (Session 6, Section 4) is itself an application of the **Options pattern** — configuration values (a connection string, provider-specific settings) supplied through a typed, composable API rather than scattered constants or magic strings read ad hoc throughout the codebase.

```csharp
public class DatabaseOptions
{
    public string ConnectionString { get; set; } = "";
    public int CommandTimeoutSeconds { get; set; } = 30;
}

builder.Services.Configure<DatabaseOptions>(builder.Configuration.GetSection("Database"));

builder.Services.AddDbContext<LeagueDbContext>((serviceProvider, options) =>
{
    var dbOptions = serviceProvider.GetRequiredService<IOptions<DatabaseOptions>>().Value;
    options.UseSqlServer(dbOptions.ConnectionString,
        sql => sql.CommandTimeout(dbOptions.CommandTimeoutSeconds));
});
```

**Why bother with a typed options class instead of just reading `IConfiguration` directly wherever it's needed:** `IConfiguration` is essentially an untyped, stringly-keyed dictionary — every read is a potential typo with no compile-time check. Binding it once into a plain class (`DatabaseOptions`) gets the same validated-property benefit the OOP guide describes for encapsulation generally: the configuration shape is defined once, checked by the compiler everywhere it's used, and easy to unit test independently of any actual configuration source.

### 5.5 A Brief Note on the Specification Pattern

For a codebase with many small, reusable, composable query conditions (`ActivePlayersSpec`, `InjuredPlayersSpec`, `TopScorersSpec`), the **Specification pattern** wraps each one as an object with a `ToExpression()` (or similar) method returning an `Expression<Func<T, bool>>`, which a generic repository method can accept and apply. It's a genuine pattern worth recognizing by name if it comes up in a codebase or an interview, but it adds a layer of indirection that's rarely worth it unless query logic is being duplicated across many places in a way that's become a real maintenance problem — for most applications, composing `IQueryable<T>` with ordinary LINQ (Sections 2–7 of LINQ Part 1 and 2) directly is simpler and just as expressive.

**Q: Should every EF Core project use the Repository and Unit of Work patterns?**

>No, and this is a genuinely contested point worth being able to discuss both sides of in an interview rather than reciting one answer. `DbContext` already provides a well-tested, LINQ-integrated abstraction over the database. Layering a repository on top is justified by specific needs — testability without a real database, a genuine multi-provider future, enforcing architectural boundaries between layers — not by habit. Doing it reflexively on every project adds indirection and boilerplate for a flexibility that, in practice, most projects never end up using.

## 6. Performance in Practice

### 6.1 N+1, Revisited

Session 5, Section 10.1 already covered this pattern and its fix (`Include`). Against a real database, it's worth actually looking at what changes: without `Include`, a loop reading `team.Players` for each of 20 teams issues 21 separate round trips to the database server, each with its own network latency — often the dominant cost, far more than the SQL execution time itself. `Include` collapses that to one round trip with one (larger) result set.

### 6.2 Cartesian Explosion — When `Include` Itself Becomes the Problem

```csharp
// Two collection Includes on the same root produces a single joined result set where
// EVERY player row is repeated once per award, and vice versa — a cartesian product
var team = await _dbContext.Teams
    .Include(t => t.Players)
    .Include(t => t.Trophies)
    .FirstAsync(t => t.Id == teamId);
```

**Why this is a real, separate problem from N+1:** a single SQL `JOIN` across two one-to-many relationships from the same root produces one row *per combination* of the two collections — a team with 25 players and 10 trophies returns 250 rows for what should conceptually be 35 pieces of data, all transferred over the network before EF Core reassembles it back into the correct shape in memory.

```csharp
var team = await _dbContext.Teams
    .Include(t => t.Players)
    .Include(t => t.Trophies)
    .AsSplitQuery()   // runs as TWO separate queries instead of one joined query
    .FirstAsync(t => t.Id == teamId);
```

`AsSplitQuery()` trades one round trip for two (or more), but each one stays a simple, non-multiplying query — often a clear net win once multiple collection `Include`s are combined, and worth knowing about specifically because the default behavior silently gets worse as more `Include` calls are added, with no compiler warning that it's happening.

### 6.3 Compiled Queries

```csharp
private static readonly Func<LeagueDbContext, int, Task<Player?>> GetPlayerByIdCompiled =
    EF.CompileAsyncQuery((LeagueDbContext context, int id) =>
        context.Players.FirstOrDefault(p => p.Id == id));

var player = await GetPlayerByIdCompiled(_dbContext, playerId);
```

Session 5, Section 5.7 covered why reflection-heavy work is typically paid once and cached rather than repeated on every call — translating a LINQ expression tree to SQL has real, similar overhead, and EF Core normally caches that translation internally already. `EF.CompileAsyncQuery` goes a step further for a genuinely hot, frequently-repeated query shape, precompiling it once explicitly. This is a targeted optimization for a query proven to be a bottleneck, not a default habit — the ordinary internal caching is enough for the overwhelming majority of queries.

### 6.4 Indexes

```csharp
modelBuilder.Entity<Player>().HasIndex(p => p.JerseyNumber);
modelBuilder.Entity<Player>().HasIndex(p => new { p.TeamId, p.Goals });   // composite index
```

An index is what lets the database find matching rows without scanning the entire table — exactly the difference between looking something up in a phone book by last name versus reading every entry in order. Every `Where`/`OrderBy`/`Join` clause used frequently, especially on a large table, is a candidate for an index on the columns it touches. The tradeoff: every index speeds up reads on that column but adds overhead to every write that touches it, so indexing everything indiscriminately isn't free either.

### 6.5 `DbContext` Pooling

```csharp
builder.Services.AddDbContextPool<LeagueDbContext>(options =>
    options.UseSqlServer(connectionString));
```

**Why this exists:** constructing a `DbContext` has some fixed cost — internal service setup, model initialization on first use. `AddDbContextPool` reuses a pool of `DbContext` instances instead of constructing a new one for every request, resetting each instance's state between uses. It's worth reaching for on a high-throughput API where that construction cost is measurable, and it comes with a real constraint: pooled contexts must not carry any custom constructor logic or mutable state beyond what EF Core itself manages, since the same instance gets reused across unrelated requests.

## 7. Cross-Cutting Concerns and Resiliency

### 7.1 Global Query Filters — the Soft-Delete Pattern

```csharp
public class Player
{
    // ...
    public bool IsDeleted { get; set; }
}

modelBuilder.Entity<Player>().HasQueryFilter(p => !p.IsDeleted);
```

Once this filter is configured, every query against `Players` — anywhere in the application, including ones written by someone who's never heard of the `IsDeleted` column — automatically excludes soft-deleted rows, without needing a `Where(p => !p.IsDeleted)` repeated at every call site. This is the same motivation as the Repository pattern's testability argument: centralizing a rule in one place so it can't be forgotten piecemeal across dozens of query call sites.

```csharp
var includingDeleted = await _dbContext.Players.IgnoreQueryFilters().ToListAsync();
```

`IgnoreQueryFilters()` is the deliberate escape hatch for the rare case (an admin recovery screen, an audit report) that genuinely needs to see filtered-out rows.

### 7.2 Logging Generated SQL

```csharp
builder.Services.AddDbContext<LeagueDbContext>(options =>
    options
        .UseSqlServer(connectionString)
        .LogTo(Console.WriteLine, LogLevel.Information)
        .EnableSensitiveDataLogging());   // DEVELOPMENT ONLY — logs actual parameter values
```

Seeing the actual generated SQL is the single most effective way to answer "why is this slow" or "why isn't this the query I expected" — it turns Section 6's performance guidance from theoretical into something you can directly confirm against real output. `EnableSensitiveDataLogging()` specifically prints real parameter values (names, salaries, anything) into logs, which is exactly why it's a development-only setting and never something to leave enabled in production.

### 7.3 Testing Strategy

| Approach | What it actually tests |
|---|---|
| EF Core InMemory provider | Model shape and basic query logic; does **not** enforce real relational constraints (foreign keys, unique indexes) and doesn't translate LINQ to real SQL, so it can pass on queries that would fail against a real database |
| SQLite in-memory | Closer to a real relational database — enforces constraints, runs real SQL — but SQLite's SQL dialect and feature set differ from SQL Server/PostgreSQL/etc., so provider-specific behavior can still diverge |
| The real provider (a test container, a dedicated test database) | The only option that verifies what actually ships; slower and more setup, but the only one that fully closes the gap |

**Why neither of the faster options is a full substitute:** both exist to make tests fast and dependency-free, which is genuinely valuable for a large test suite — but that speed comes from *not* being the real database, which means neither one can catch a bug that only manifests against the real provider's specific SQL translation or constraint enforcement. A mature test suite typically uses fast in-memory/SQLite tests for the bulk of everyday logic, with a smaller set of tests running against the real provider (often via a disposable container) specifically for anything relying on provider-specific behavior.

### 7.4 Connection Resiliency — Retrying on Transient Failure

A production database connection fails sometimes for reasons that have nothing to do with the query itself — a brief network blip, a cloud database failing over, a connection pool exhausted for a moment. Left alone, EF Core throws on the first such failure exactly like any other error. `EnableRetryOnFailure` configures an automatic retry strategy for exactly this class of problem:

```csharp
builder.Services.AddDbContext<LeagueDbContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("League"),
        sql => sql.EnableRetryOnFailure(
            maxRetryCount: 3,
            maxRetryDelay: TimeSpan.FromSeconds(5),
            errorNumbersToAdd: null)));
```

EF Core detects whether a given failure is the kind considered transient (worth retrying) or not (a genuine query error, not worth retrying), and only retries the former, waiting between attempts, up to `maxRetryCount` times before finally letting the exception through.

**Why this interacts awkwardly with explicit transactions (Section 1.2), and what to do about it:** if a retry strategy is enabled and a failure happens partway through a manually-opened transaction (`BeginTransactionAsync`), simply retrying the failed operation isn't safe — some statements in that transaction may have already partially applied. EF Core actually refuses to let you combine `BeginTransactionAsync` directly with a retrying execution strategy; it throws rather than risk that inconsistency. The fix is to make the whole transaction the unit that gets retried, not just the failing statement inside it:

```csharp
var strategy = _dbContext.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    using var transaction = await _dbContext.Database.BeginTransactionAsync();

    var team = new Team { Name = "Pyramids FC" };
    _dbContext.Teams.Add(team);
    await _dbContext.SaveChangesAsync();

    _dbContext.Players.Add(new Player { Name = "New Signing", TeamId = team.Id });
    await _dbContext.SaveChangesAsync();

    await transaction.CommitAsync();
});
```

**Q: Is `EnableRetryOnFailure` something every project should turn on?**

>For anything talking to a cloud-hosted database (Azure SQL, most managed Postgres/MySQL offerings), yes — transient faults there are a normal, expected occurrence, not an edge case, and the built-in retry strategy is specifically designed around exactly that. For a database running on the same local network with a stable connection, it matters much less, though it's rarely harmful to leave on. The part that actually needs deliberate attention is Section 1.2's explicit-transaction case — that's the one place enabling retries changes how existing code needs to be written, not just a configuration flag flipped with no other consequences.

## 8. Putting It All Together — A Worked Capstone Example

A minimal but complete shape, combining a repository (Section 5.2), the factory pattern for a background job (Section 5.3), eager loading with a split query (Section 5 of Part 2 and Section 6.2 here), and async end to end (LINQ Part 2, Section 8).

```csharp
// Entities (Part 1, Section 3.1; Part 2, Section 2.1)
public class Team
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public List<Player> Players { get; set; } = new();
}

public class Player
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public int Goals { get; set; }
    public int TeamId { get; set; }
    public Team Team { get; set; } = null!;
}

// DbContext (Part 1, Section 3.3; Part 2, Section 1.2)
public class LeagueDbContext : DbContext
{
    public LeagueDbContext(DbContextOptions<LeagueDbContext> options) : base(options) { }

    public DbSet<Team> Teams => Set<Team>();
    public DbSet<Player> Players => Set<Player>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Player>()
            .HasOne(p => p.Team)
            .WithMany(t => t.Players)
            .OnDelete(DeleteBehavior.Restrict);   // Section 3, Part 2
    }
}

// Repository (Section 5.2) — the boundary between the domain and EF Core specifics
public interface ITeamRepository
{
    Task<List<TeamSummary>> GetTeamSummariesAsync(CancellationToken cancellationToken);
}

public class TeamRepository : ITeamRepository
{
    private readonly LeagueDbContext _dbContext;
    public TeamRepository(LeagueDbContext dbContext) => _dbContext = dbContext;

    public Task<List<TeamSummary>> GetTeamSummariesAsync(CancellationToken cancellationToken) =>
        _dbContext.Teams
            .AsNoTracking()                                  // read-only — Section 7, Part 2
            .Select(t => new TeamSummary(t.Name, t.Players.Count, t.Players.Sum(p => p.Goals)))
            .OrderByDescending(s => s.TotalGoals)
            .ToListAsync(cancellationToken);
}

public record TeamSummary(string TeamName, int PlayerCount, int TotalGoals);

// A background job using the factory pattern (Section 5.3) instead of a scoped DbContext
public class NightlyStandingsJob
{
    private readonly IDbContextFactory<LeagueDbContext> _contextFactory;
    public NightlyStandingsJob(IDbContextFactory<LeagueDbContext> contextFactory) => _contextFactory = contextFactory;

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        await using var dbContext = await _contextFactory.CreateDbContextAsync(cancellationToken);
        var repository = new TeamRepository(dbContext);

        var summaries = await repository.GetTeamSummariesAsync(cancellationToken);
        foreach (var summary in summaries)
            Console.WriteLine($"{summary.TeamName}: {summary.PlayerCount} players, {summary.TotalGoals} goals");
    }
}
```

**Why walk through this specifically:** every individual piece traces back to a specific "why" from across all three sessions — `AsNoTracking` because this is read-only, a projection into `TeamSummary` instead of `Include` because only three derived values are needed (not the full `Player` entities), `Restrict` instead of the cascade default because losing a team's players silently is a real risk, and the factory pattern specifically because a background job has no request to scope a `DbContext` to. None of these choices are arbitrary once each session's reasoning is in place — that's the real target for this series: not memorizing what each API call does, but being able to justify why it's the right call in a given situation.

## 9. Quick Reference — Glossary

| Term | Meaning |
|---|---|
| Implicit transaction | The automatic transaction wrapping every single `SaveChanges`/`SaveChangesAsync` call |
| Explicit transaction | A transaction spanning multiple `SaveChanges` calls, via `BeginTransactionAsync`/`CommitAsync`/`RollbackAsync` |
| Optimistic concurrency | Detecting conflicting concurrent edits at save time (via a row-version/timestamp column) rather than locking rows while they're being edited |
| `DbUpdateConcurrencyException` | Thrown when a save's `WHERE` clause matches zero rows because the row changed since it was loaded |
| `DbUpdateException` | Thrown when the database rejects a save for a reason other than a concurrency mismatch — a unique constraint, a required column, a broken foreign key |
| `FromSqlInterpolated` / `FromSqlRaw` | Escape hatches for raw SQL queries the LINQ translator can't or shouldn't express |
| `ExecuteUpdate` / `ExecuteDelete` | Translates a LINQ query directly into a single `UPDATE`/`DELETE` statement against the database, bypassing the change tracker entirely |
| Unit of Work | Grouping several operations to commit or fail together as one; `DbContext` already implements this |
| Repository pattern | An interface abstracting persistence behind domain-shaped methods, decoupling callers from EF Core specifics |
| Factory pattern (`IDbContextFactory<T>`) | Creates fresh, independent `DbContext` instances on demand, for code not scoped to a single request |
| Options pattern | Typed, validated configuration objects bound from `IConfiguration`, instead of untyped string lookups |
| Specification pattern | Reusable, composable query conditions wrapped as objects, applied by a generic repository method |
| N+1 problem | One query per loop iteration instead of one query total; fixed with `Include` |
| Cartesian explosion | Multiple collection `Include`s on the same root multiplying the result set size; fixed with `AsSplitQuery` |
| Compiled query | A LINQ-to-SQL translation precompiled once and reused, for a proven hot path |
| Index | A database structure that speeds up lookups on specific columns, at some cost to writes on those columns |
| `DbContext` pooling | Reusing a pool of `DbContext` instances instead of constructing a new one per request |
| Global query filter | A `Where` condition automatically applied to every query against an entity, e.g. for soft deletes |
| `IgnoreQueryFilters` | Deliberately bypasses global query filters for the rare case that needs to see filtered-out rows |
| `EnableRetryOnFailure` | Configures automatic retries for transient database failures; requires an execution strategy wrapper around explicit transactions |
| Execution strategy | The object EF Core uses to retry an operation on transient failure; explicit transactions must be wrapped in one when retries are enabled |
